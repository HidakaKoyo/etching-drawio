# 修復ループの規律

- 対象: `.drawio` を直すエージェント
- **実装契約の正本は repo の `contracts/delivery.md` §2 と `contracts/exit-codes.md`。** ここはそれを、判断が要る箇所だけ平易にしたもの。食い違ったら `contracts/` が正しい

## 1. 触ってよいファイル

修復中に書き換えてよいのは**作業コピーだけ**である。正本 (`.drawio` そのもの) は、最後に `etch deliver --content` が置換するまで一度も変わらない。

作業コピーは**正本と同じディレクトリ**に置く。別 filesystem 上の temp に置くと、最後の置換が rename でなく copy + unlink になり、途中で見える瞬間ができる。

途中経過を正本に書き戻すと、失敗して止まったときに壊れた図が残る。それを避けるための規律なので、「どうせ最後に直すから」で崩さない。

納品が通ったら作業コピーを消す。正本と同じディレクトリに `.drawio` が 2 つ残っていると、次に開く人がどちらが正本か分からない。**失敗して止まったときだけ残す** (そのときは証拠なので消さない)。

## 2. fix set

1 周に当てる修正のまとまりを fix set と呼ぶ。条件は 2 つある。

- **互いに競合しない** — 同じ cell の同じ属性を 2 つの修正が別の値にしようとしない
- **決定的である** — 同じ入力と同じ診断からは、いつ実行しても同じ結果になる

診断 10 件を一息に直すのは構わない。上の 2 条件を満たすなら 1 fix set である。逆に、直し方が診断だけからは決まらないもの (どのレイアウトが読みやすいか、どのラベルが正しいか、欠けた ID はどの図形を指すはずだったのか) は機械的な修正ではない。**判断の根拠を述べたうえで直し、それも 1 周として数える。** 根拠を書かずに黙って選ぶと、あとから誰も検算できない。

停止条件の数え方は、機械的な fix set も判断を伴う直しも同じである。「これは判断だから 5 回に含めない」という抜け道は作らない。

**1 fix set ごとに必ず再検証する。** 2 つ当ててからまとめて検証すると、どちらが効いたのか分からなくなり、循環検知の fingerprint も意味を失う。

## 3. 診断の読み方

`diagnostics[]` の 1 件は `code` / `severity` / `message` / `subject` / `evidence` を持つ。

- `code` が何の違反かを決める。`xml/*` は構造、`input/*` は入力ポリシー、`security/*` は外部参照、`export/*` は書き出し後、`delivery/*` は納品段
- `subject.file` / `subject.xpath` / `subject.cellId` が直す場所を指す。`cellId` があるならその cell を直す
- `evidence.expected` / `evidence.actual` は、何が来るべきで何が来たかを示す。ここが直しの根拠になる
- `severity: warning` の診断は required check を落とさない。直せるなら直すが、直せなくても納品はできる

同じ code が大量に出た場合、CLI は code ごとに 50 件で打ち切り、打ち切った旨の診断を 1 件足す。件数が 50 で頭打ちになっていたら、直したあと再検証で残りが出てくる。

`supportedFixes` フィールドは schema にあるが、v1 の CLI はこれを埋めない。**修正内容はエージェントが決める。** 空だからといって「直しようがない」と判断しない。

## 4. 停止条件

次のいずれかに当たったら、その場で止めて failed を報告する。**納品してはいけない。**

### 循環

状態 fingerprint が、これまでに出たものと同じになったとき。

```
fingerprint = 作業コピー自体の SHA-256
            + 正規化した (code, subject) の multiset
```

毎周この 2 つを記録し、既出集合と突き合わせる。作業コピーの hash は export 前の検証失敗でも必ず取れるので、fingerprint は常に計算できる。

一致は「同じ場所をぐるぐるしている」ことを意味する。あと 1 周で抜けられる見込みがあっても続けない。

### 打ち切り

fix set の適用が **5 回**に達したとき。

### 止めない場合

**診断が減っている限り、同じ code の再発だけでは止めない。** 同じ違反が別の cell で次々に見つかるのは前進であって循環ではない。判定するのは fingerprint であって、code の見た目ではない。

## 5. 止まったときの報告

- 正本は開始時のまま無傷である。そう明記する
- 作業コピーは捨てず、パスを添える
- 最後の診断 (code と subject) を添える
- 何周回ったか、止めた理由 (循環 / 打ち切り) を書く

「直せなかった」だけで終えない。どこまで減らせて、何が残ったかを書く。

## 6. exit code の扱い

| code | 意味 | 修復ループでの扱い |
|---|---|---|
| 0 | 通った | 納品へ進む |
| 1 | 検証で落ちた | 修復ループを回す対象 |
| 2 | 書き出し・出力検証で落ちた | 図の問題とは限らない。診断を読んで切り分ける |
| 3 | hash 競合 | **再試行しない。** 誰かが正本を触っている。報告して止まる |
| 4 | 引数・profile が不正 | 自分の呼び出しかたを直す。JSON は出ない |
| 5 | 依存欠落 | 環境の問題。`references/environment.md` を見て報告する |
| 6 | CLI 内部エラー | 入力のせいではない。再試行せず報告する |

exit 3 で `--content` を付け直して再実行するのは、他人の編集を踏み潰す操作になる。やらない。
